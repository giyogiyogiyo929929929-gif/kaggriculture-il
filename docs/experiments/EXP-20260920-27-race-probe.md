# EXP-20260920-27: metav4_v13 の `_RACE` 層は実際には効いていない（候補G の中止）

日付: 2026-09-20
関連 doc: 07 §3 候補A・候補D, EXP-20260920-23（層の読み取り）, EXP-20260920-26（候補F の失敗と教訓）
コミット: 未コミット

## 仮説

EXP-20260920-26 で、`metav4_v13` の telemetry を読んで「本体は `_RACE` 層（クローン検知＋horizon 24 の予約）」と考えた。
**404〜476 ターンも動いている**ので、こちらの候補A（コピー確定時に先読み 52）と同じ土俵に立てていないのではないか。
→ 候補G として「ミラー戦での予約の効かせ方」に手を入れる。

## 設定：予約の実体を測る

v9/4 系の予約（`_r36_reserve`）は、horizon をこう決める（`submissions\v7_relax\main.py` 1682〜1683 行、3996〜3997 行）：

```py
_v9_hz = _V9_ITEM_HZ.get(player)          # v9 の RACE 層が毎ターン入れる
end = min(695, step + (max(_v9_hz.values()) if _v9_hz else _R37_HORIZONS.get(player, 2)))
```

- **`_V9_ITEM_HZ` があれば、そちらが使われる。`_R37_HORIZONS` は `_V9_ITEM_HZ` が空のときだけ見られる。**
- `metav4_v13` の `_RACE` 層が 24 に書き換えるのは **`_R37_HORIZONS` のほう**（`_r36_reserve` の中で一時的に差し替える）。

そこで `metav4_v13` を名前空間ごと読み込み、**`_RACE_ORIG_RESERVE` を記録つきの関数に差し替えて**、
予約のたびに `_V9_ITEM_HZ` があるか・その horizon はいくつかを数えた（`metav4_v13` のファイルは改変していない）。

## 結果（v10 との1試合、seed 1）

| 測ったもの | 値 |
|---|---|
| `_r36_reserve` の呼び出し | **719回**（毎ターン） |
| うち `_V9_ITEM_HZ` があった | **719回（100%）**。horizon は**常に 40** |
| うち `_V9_ITEM_HZ` が空だった | **0回** |
| → `_R37_HORIZONS`（＝`_RACE` 層が 24 にするもの）が使われた回数 | **0回** |
| `_RACE_REPORT` | clone 404ターン・horizon 404ターン・mirror 1・エスカレート0 |

**`_RACE` 層は 404 ターンにわたって `horizon=24` を設定しているが、その値は一度も読まれていない。**
`_V9_ITEM_HZ` が毎ターン埋まっているので、予約は常に v9 の RACE 層の horizon 40 で走る。

## 分かったこと

1. **候補G は不要。** 相手の `_RACE` 層は、候補F の元にした `_y_preguard` と同じく**「あるけど効いていない」層**だった。
   EXP-20260920-26 の教訓（発火回数を測る）をもう一段進めて、**「発火した値が実際に使われているか」まで測る必要があった。**
2. **予約の horizon はこちらのほうが長い。** `metav4_v13` は常に 40。
   v7/v10 は候補A により、**コピーと確定した試合では 52**（`V9_RACE_DEFAULT`/`V9_RACE_MAX` を差し替え）。
   「同じ土俵に立てていない」という EXP-20260920-26 の考察2・3 は**誤りだったので取り消す**。
3. したがって `metav4_v13` の優位は末尾の層ではない。**v9/4 とは先頭 304,518 バイトしか一致しない**（EXP-20260920-23）ので、
   **中盤の層・テープ・定数そのものが違う＝土台が違う**とみるのが自然。

## 追試：`metav4_v13` は手元の公開26本に対して強いのか（seed 241〜250、各20試合）

土台を乗り換える価値があるかを決めるため、**v10 とまったく同じ相手・同じ seed** で `metav4_v13` を走らせた。

| | **v10（いまの提出）** | `metav4_v13` |
|---|---|---|
| 26本の合計（ペア単位） | **202勝 58敗** | 195勝 65敗 |
| 相手ごとに上回った数 | **10本** | 4本 |

- **`metav4_v13` が上回るのは4本だけ**：`jaxa_2802`（10-0 対 v10 8-2）、`shop_router_v7`（10-0 対 8-2）、
  `ready_stock`（7-3 対 6-4）、`v47`（6-4 対 5-5）。
- **v10 が上回る10本には、コピー系がまとめて入っている**：
  `gods_mode` 10-0 対 8-2、`peak_2950` 10-0 対 8-2、`smaller_market_shock` 10-0 対 8-2、
  `thomas_v94_safe` 10-0 対 9-1、`yummers` 10-0 対 9-1。
  **`metav4_v13` にはコピー狩り（候補A・A2・A3）に当たる機構が無い**ので、ここで落としている。
- `k256_h2_q_v1` には `metav4_v13` が 7勝3敗（v10 は別 seed で 13勝7敗）。

→ **土台の乗り換えは不要。** `metav4_v13` は**v10 との直接対決に強いだけ**で、
全体の勝率では v10 が上。最終順位は締め切り後の Bradley-Terry トーナメント（全体の勝敗）で決まる（doc 06）ので、
**全体に強い v10 を維持するのが正しい。**

## 結論

1. **候補G は中止**（相手の `_RACE` は効いていない。予約の horizon はこちらが 52、相手は 40）。
2. **metav4_v13 を土台にする案も見送り**（全体では v10 が上。コピー狩りを失うほうが痛い）。
3. **`metav4_v13` は「相性の悪い1本」として受け入れる。** ただし 9/23 の公開締め切りまでにコピーが広まる可能性はある
   （取得時の票数は11）。**広まり方を見て、必要なら対策を考える。**
