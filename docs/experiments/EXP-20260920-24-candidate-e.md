# EXP-20260920-24: 候補E（同じターンに出す SELL の並べ替え）の実装と評価

日付: 2026-09-20

## 仮説

`metav4_v13` に負ける主因は、**同じターンに複数の品を売るときの順序**（EXP-20260920-23）。
市場は1個ずつ約定して売るほど値が下がるので、順序だけで手取りが変わる。
v9/4（＝v4〜v8 の土台）はテープの順のまま売っている。**順序だけを最適化すれば詰められる**はず。

## 設定

- 実装：`submissions\v9_reorder\main.py`＝**v7 の末尾に候補E の層を足したもの**（v7 の先頭 864,304 バイトはそのまま）。
  候補D（v8）とは独立に測るため、土台は v7 にした。
- 中身：`action["market"]` の中の**連続する SELL のかたまり（2〜6件）**について全順列を試し、
  「自分の手取り − 相手の手取り」が最大になる並びを選ぶ。**注文の品目と数量は一切変えない。**
  相手の注文は見えないので、**相手も同じ注文列を出す（＝コピー）と仮定する**（metav4_v13 の `_v44y_lockstep` と同じ考え方）。
- 約定の再現は `kaggle_environments` の実装を読んで書いた（doc 07 §3 E.1b）。**推測していない。**
- 1ターンの探索は 25ms で打ち切る（NFR-1）。step 216 以降だけ動く。
- 機構の出典：`thomastschinkel/the-metav4-farm-submission-v13`（Apache-2.0）の `_v44y_reorder`。

## 結果1：テストと preflight

- `tests\test_v9_reorder.py` **13件すべて合格**。うち2件は**エンジンとの一致**を直接確かめるもの：
  - 層の価格関数が `market_price` と全品目・8通りの在庫で一致
  - 1品目の約定の再現が、エンジンの `_commit_unit` を回した結果と一致（手取りが両者とも一致）
- preflight **全項目 OK**。1ターンの推論は **中央値 0.62ms / 99%点 5.59ms / 最悪 47.23ms**（NFR-1 は最悪200ms・99%点50ms）。

### 踏んだ落とし穴

層の先頭で `from time import perf_counter` をしたら、**それが「最後の callable」になって内側として掴まれた**。
preflight が `TypeError: time.perf_counter() takes no arguments (2 given)` で止めた。
内側を捕まえてから import するように直し、`test_inner_is_the_v7_agent` で再発を止める。

### 受け入れ条件の書き方を直した

E.3 の「コピー3本に各20試合で**全勝**を保つ」は、**v7 自身が seed 1〜20 では 19勝1敗**なので満たせない条件だった
（EXP-20260920-21 が使った seed 141〜200 では v7 が 60勝0敗だったため、そう書いてしまった）。
**「v7 から退行しない（ペア差・勝敗ともに v7 以上）」に読み替える。** doc 07 §3 E.3 を直した。

## 分かったこと

1. **順序の最適化は、相手を選ばず効く。** コピー相手にも、別系統にも、v49/v50 系にも、金額が一様に良くなった。
   26本で勝ち数が減った相手はゼロ。**候補D と違って「コピー戦では止める」必要がない。**
2. **効果の大きさは1試合あたり数百ドル**。勝敗が変わるのは僅差の試合だけなので、勝ち数の伸びは 189→196（+7）にとどまる。
3. **metav4_v13 には届いていない。** 相手には順序の最適化に加えて `_RACE` のエスカレート（先回りされたら horizon 24）と
   `_y_preguard`（day-end guard の前倒し）がある。**候補F を足さないと差は埋まらない**と考えられる。
4. エンジンの約定ルールを写したテストが役に立った。**価格の再現と1品目の約定の再現を直接テストしたので、
   「見積もりが実際と違う」類の間違いは潰せている。**
